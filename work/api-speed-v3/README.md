# BALL46 manual Bulk refresh V3

The owner controller supports manual 30/15/10-second selection through the current HUB Durable Object. Loading the controller never changes cadence or calls 5USD. Production remains at its existing 30 seconds until the owner presses Save.

The account window is read from X-RateLimit-Limit/Remaining/Reset on existing Bulk responses. These are provider-reported account totals across API keys, with an observation time and fixed-window expiry. They are not an exact rolling-60-second counter, and other Workers are not represented as centrally reserved consumers. Acceleration requires the observed Ultra limit of 40, a current window, an observation no older than 30 seconds, and at least 20 requests of headroom plus the chosen cadence and pending HUB reservations. Extra live requests are additionally limited to two/minute at 15s and four/minute at 10s. Lost/expired evidence falls back to the original 30s baseline slot without overwriting the owner's selected configuration.

HTTP 429 persists cooldown across restarts, honors numeric/date Retry-After, and stops new Bulk live/today requests during cooldown. HTTP 401/402/403 disables acceleration and retains the original baseline behavior; no billing, subscription or provider key is changed. The code does not claim to prevent an unrelated account/subscription HTTP 402.

Only the HUB main module and three helper modules, plus the isolated owner controller entry/page/client/helper, are changed. Existing namespaces, all data merge/normalization/snapshot functions, Rich Odds class, Website, Engine, Full Market, Member, Stripe and Cron are preserved. Source generation requires the exact current HUB hash and reconstructs the original bytes after removing all 13 approved edits. All faster modes are tested against isolated fixtures, not by changing Production cadence.

Validation: `node policy.test.mjs` (34), `node integration.test.mjs` (18), plus PC 1366x900 and mobile 390x844 manual Save/DEFAULT, quota loss, cooldown and connection recovery. Release captures fresh Active versions/settings/Cron, verifies the owned staged secret lineage, checks exact uploaded module hashes and bindings, and waits for existing normal Bulk responses to supply real quota evidence. No verification step forces an upstream refresh.

Rollback: capture the immediate pre-release HUB/owner versions in `production-audit/api-speed-v3-release.json`. If the owner has since selected 15/10, first use DEFAULT to return to 30 and verify Server confirmation; do not restore the older HUB while a 10-second raw setting remains. Restore only the captured HUB and owner versions with leases against the owned current versions. New telemetry/audit keys can remain, since the older source ignores them. The automatic failure path performs the same ownership check and holds rollback if it detects an owner cadence change. Protected Website/Engine/Full Market versions must match the fresh baseline.
